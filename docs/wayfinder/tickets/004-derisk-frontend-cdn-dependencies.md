## Question

[templates/index.html](../../../src/cooklang_kitchen/templates/index.html) loads two dependencies from CDN in production (not just dev):

1. `https://cdn.jsdelivr.net/npm/@tailwindcss/browser@4` — this is Tailwind's "Play CDN" / in-browser JIT build. Checked against Tailwind's own docs (via context7): it is explicitly "meant for development purposes only" — every page load re-runs the JIT compiler in the browser instead of shipping a pre-built stylesheet.
2. `https://cdn.jsdelivr.net/npm/alpinejs@3.x.x/dist/cdn.min.js` — pinned only to major version `3.x.x`, so any 3.y.z release (including breaking minor/patch changes) is pulled automatically on next page load. Neither script tag has a Subresource Integrity (SRI) hash, so a compromised or unavailable CDN can silently break or replace the app's JS/CSS.

Decide: introduce a real Tailwind build step (Tailwind CLI, per official recommendation) as part of the Docker build, and/or pin Alpine to an exact version with an SRI hash, and/or vendor both locally. Given the Dockerfile ([Dockerfile](../../../Dockerfile)) already does a `pip install` build step, adding a Node-based CSS build stage is a real (if small) infra change — weigh that against just pinning+SRI as a lower-effort interim fix. Write up the chosen approach as an implementable spec.

## Answer

Four decisions:

1. **Real Tailwind CLI build**, not pin+SRI on the Play CDN — matches Tailwind's own production guidance and removes the in-browser JIT cost entirely.
2. **Standalone CLI (no Node)** in a multi-stage Docker build — the final runtime image never gets Node or the Tailwind CLI, only the compiled CSS.
3. **One template for dev and prod** — no `app.debug` branching; local dev runs the same standalone CLI (`--watch`), documented in the README.
4. **Alpine.js**: pinned to an exact version with an SRI hash (not vendored) — its CDN build is production-grade already; the only gaps were the floating `@3.x.x` tag and missing SRI.

### Implementation (done)

- [src/cooklang_kitchen/static/css/input.css](../../../src/cooklang_kitchen/static/css/input.css) (new): `@import "tailwindcss" source(none);` with explicit `@source` directives for `templates/` and `static/js/` — `source(none)` disables Tailwind's automatic whole-project content detection, which otherwise picks up stray text in `README.md`/`docs/` and produces a non-deterministic build depending on what else happens to be in the working tree. This makes local and Docker builds byte-identical (confirmed: 46625 bytes locally vs 46623 in the container, the 2-byte gap being a CRLF/LF artifact).
- [Dockerfile](../../../Dockerfile): new `css-builder` stage (`alpine:3.20` + `curl`/`libstdc++`/`libgcc` — the musl standalone binary still dynamically links libstdc++) downloads the pinned `tailwindcss-linux-x64-musl v4.3.3` binary and compiles `static/css/app.css --minify`; the final `python:3.12-slim` stage only `COPY --from=css-builder` the compiled CSS, no Tailwind CLI or Node in the shipped image.
- [templates/index.html](../../../src/cooklang_kitchen/templates/index.html): `<script src="https://cdn.jsdelivr.net/npm/@tailwindcss/browser@4">` replaced with `<link rel="stylesheet" href="{{ url_for('static', filename='css/app.css') }}">`; Alpine pinned to `alpinejs@3.15.12` with `integrity="sha384-pb6hrQvo4s23cEUFtj0CZkzGE3jyK3pj26RIupXXxhSrrcUA/Cn0lZgcCrGH0t6L"` and `crossorigin="anonymous"` — the SRI hash was computed locally from the downloaded file (`openssl dgst -sha384`) and cross-checked against jsdelivr's own published sha256 for the same file, not trusted from a third-party source.
- [.gitignore](../../../.gitignore): `src/cooklang_kitchen/static/css/app.css` added — it's a build artifact regenerated by both the Docker build and local dev, same as the Docker build's own output.
- [README.md](../../../README.md): new "CSS" subsection documenting the one-time standalone CLI download and `--watch` command for local dev.
- Verified end-to-end: built the actual Docker image with `podman` (installed and available locally, used in place of `docker` which isn't installed), ran the container, confirmed `/static/css/app.css` serves a real compiled stylesheet (arbitrary-value colors, the 3-column arbitrary grid-cols layout, dark-mode variants all present), `GET /healthz` and `GET /api/recipes` both responded correctly, and container logs were clean. Also ran the local dev server standalone and confirmed it serves byte-identical CSS and the same pinned Alpine tag. All test containers/images and the temporary CLI binary were cleaned up afterward.
- Found and fixed one bug along the way: the standalone `tailwindcss-linux-x64-musl` binary needs `libstdc++`/`libgcc` even on Alpine (musl) — a plain `apk add curl` build failed with dynamic-linking errors; caught by actually building the image rather than assuming the Dockerfile was correct.
